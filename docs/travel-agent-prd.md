# 旅行助手智能体 PRD（MVP）

**产品名称**：Travel Agent  
**版本**：V1.0（MVP）  
**目标平台**：Web 优先，移动端响应式适配  
**目标用户**：计划自由行的个人、情侣、家庭及朋友结伴用户

## 1. 产品目标

帮助用户通过对话快速生成可执行、可修改、可保存的个性化旅行计划。

MVP 成功标准：

- 用户在 5 分钟内获得首版行程。
- 行程包含每日安排、交通建议、住宿区域、预算估算和注意事项。
- 用户能通过一句自然语言完成局部修改。
- 用户可以保存和分享行程。

非目标：

- 首期不直接完成机酒支付与预订。
- 不承诺实时最低价。
- 不提供签证代办、保险销售或人工客服。

## 2. 用户与场景

| 用户 | 典型场景 | 核心诉求 |
|---|---|---|
| 首次自由行用户 | “去日本玩 6 天怎么安排？” | 有清晰、不踩坑的完整方案 |
| 时间有限的上班族 | “周末从上海去周边两天” | 快速完成决策 |
| 家庭出游者 | “带老人和孩子去北京” | 节奏轻松、交通便利 |
| 结伴旅行组织者 | “三个人预算各 5000” | 兼顾多人偏好和预算 |
| 深度旅行者 | “想避开热门景点，逛本地街区” | 个性化和差异化路线 |

## 3. 核心使用流程

```text
进入产品
  ↓
输入旅行意图
  ↓
智能体提取条件，必要时追问
  ↓
展示旅行需求确认卡片
  ↓
生成首版行程
  ↓
用户查看每日计划与预算
  ↓
用户提出修改 / 锁定安排
  ↓
局部重规划
  ↓
保存、分享或导出
```

## 5. 功能需求

### 5.1 首页与旅行创建

用户可通过自然语言或表单开始。

输入示例：

> 10 月从上海出发去东京和京都 7 天，2 个人，人均 9000，喜欢美食和红叶，不想每天太赶。

首屏内容：

- 对话输入框。
- 常用快捷示例。
- 最近保存的行程。
- “新建旅行”按钮。

系统应支持从输入中提取：

| 字段 | 是否必填 | 示例 |
|---|---:|---|
| 出发地 | 否 | 上海 |
| 目的地 | 是 | 日本 / 东京 |
| 日期或时长 | 至少一项 | 10 月 1–7 日 / 7 天 |
| 出行人数 | 否 | 2 人 |
| 预算 | 否 | 人均 9000 元 |
| 出游类型 | 否 | 情侣、亲子、家庭、朋友 |
| 兴趣偏好 | 否 | 美食、自然、购物、博物馆 |
| 节奏偏好 | 否 | 慢节奏、紧凑、平衡 |
| 限制条件 | 否 | 不自驾、少走路、避开人群 |

### 5.2 智能追问

若核心信息不足，系统按优先级追问，单次最多问 2 个问题。

优先级：

1. 目的地。
2. 日期或旅行时长。
3. 出发地（涉及跨城或跨国交通时）。
4. 人数与预算。
5. 偏好与限制。

示例：

> 你计划从哪里出发？大约安排几天时间？

系统不应反复询问用户已经提供过的信息。

### 5.3 旅行需求确认卡

在生成前展示可编辑的结构化卡片，避免模型理解偏差。

```text
目的地：东京、京都
时间：2026 年 10 月 1 日至 7 日，共 7 天
出发地：上海
人数：2 人
预算：人均 9000 元
偏好：美食、红叶、慢节奏
限制：减少换酒店
```

操作：

- 点击字段编辑。
- 增加或删除偏好。
- 点击“生成行程”。
- 点击“继续补充需求”。

### 5.4 行程生成

系统生成按天组织的行程，并以可展开卡片展示。

每日行程字段：

| 字段 | 说明 |
|---|---|
| 日期与城市 | 第几天、所在城市、星期信息 |
| 当日主题 | 如“浅草与东京老城漫步” |
| 时间段安排 | 上午、下午、晚上 |
| 地点与活动 | 景点、街区、餐饮或体验 |
| 推荐理由 | 与用户偏好的关联 |
| 建议停留时长 | 如 1.5–2 小时 |
| 交通建议 | 步行、地铁、巴士、城际列车等 |
| 预算预估 | 当日预计花费区间 |
| 注意事项 | 预约、闭馆、天气、拥挤等 |

每日计划示例：

```text
Day 2｜东京｜浅草与上野文化漫步
上午：浅草寺、仲见世商店街（约 2 小时）
下午：上野公园、阿美横町（约 3 小时）
晚上：居酒屋或拉面店晚餐

交通：地铁为主，总通勤约 45 分钟
步行：约 7 公里
预算：¥700–¥1,100 / 人
提示：浅草寺建议上午抵达，避开午后人流。
```

### 5.5 行程概览

固定展示在行程详情顶部：

- 目的地与日期。
- 总天数。
- 出行人数。
- 总预算与人均预算。
- 城市路线。
- 住宿晚数。
- 行程密度标签：轻松 / 平衡 / 紧凑。
- 最近更新时间。

### 5.6 预算模块

预算以“估算区间”展示，避免精确价格误导。

| 分类 | 内容 |
|---|---|
| 大交通 | 往返机票、跨城交通 |
| 住宿 | 按住宿档位和晚数估算 |
| 市内交通 | 地铁、出租车、公交等 |
| 餐饮 | 每日餐饮消费 |
| 景点活动 | 门票、体验与预约项目 |
| 预留金 | 购物、临时开支与汇率波动 |

预算状态：

- `预算充足`：预计总价低于预算 85%。
- `接近预算`：预计总价为预算的 85%–100%。
- `可能超支`：预计总价超过预算。

当预算超支时，提供调整建议：调整住宿档位、缩短跨城市程、减少付费体验、更换出行日期，或使用公共交通替代出租车。

### 5.7 修改与局部重规划

用户可自然语言提出修改，也可对某一天点击“调整”。

| 类型 | 示例 |
|---|---|
| 修改目的地 | “不要大阪，京都多住两晚” |
| 修改节奏 | “每天最多安排两个景点” |
| 修改预算 | “控制到每人 6000 元以内” |
| 替换活动 | “把博物馆换成适合孩子的地方” |
| 固定内容 | “第三天的迪士尼不要变” |
| 增加条件 | “优先推荐有电梯的地铁路线” |
| 局部重排 | “重排后两天，不动前四天” |

重规划规则：

- 被用户锁定的内容不可自动更改。
- 优先重排受影响日期，不重做整份行程。
- 每次修改后展示变更摘要。
- 预算、通勤和住宿建议需要同步更新。

### 5.8 住宿与交通建议

住宿模块展示区域推荐，不要求首期提供实时可订酒店。

住宿区域卡片包括区域名称、适合人群、优势与注意事项、主要景点通勤便利度、建议每晚价格区间与推荐住宿晚数。

交通模块包括到达目的地建议、城市间移动建议、市内交通方式、机场或车站往返建议，以及交通卡、通票或租车建议。

### 5.9 保存、分享与导出

MVP 功能：

- 自动保存草稿。
- 手动保存行程。
- 复制为 Markdown 或纯文本。
- 生成只读分享链接。
- 分享页隐藏用户私密备注。
- 分享链接使用独立随机令牌，可由行程所有者撤销或轮换；公开响应不得暴露可编辑接口所需的完整旅行对象。

后续功能：PDF 导出、日历导入、地图路线同步、团队协作编辑。

### 5.10 行前准备清单

- 根据目的地、旅行时间、同行人和行程内容生成 6–20 条准备事项。
- 支持证件、预订、行李、健康、支付和其他六类事项。
- 支持用户手动添加、勾选完成和删除，完成进度需跨刷新保留。
- 重新生成时保留已有完成状态和未重复的手动事项。
- 涉及签证、入境、保险或健康政策时，只提示用户向官方渠道核对，不把模型知识作为实时结论。

## 6. 页面需求

### 6.1 首页

- 顶部导航：Logo、我的行程、设置。
- 主标题：描述产品价值。
- 大型输入框：支持自然语言输入。
- 快捷标签：周末游、亲子游、情侣游、预算游、深度游。
- 最近行程列表。

### 6.2 对话与需求确认页

```text
左侧：对话记录与输入框
右侧：旅行需求确认卡
底部：生成行程按钮
```

要求：对话过程可回看；已提取字段实时更新；用户可手动编辑字段；生成期间展示“正在规划路线”“正在核算预算”等步骤状态。

### 6.3 行程详情页

```text
顶部：行程概览、预算状态、保存 / 分享
左侧：Day 1 至 Day N 导航
中间：每日行程卡片
右侧：智能助手对话与修改记录
```

关键操作：编辑某天、锁定某项安排、删除某项安排、新增活动、调整旅行节奏、查看变更记录。

## 7. 智能体业务规则

### 7.1 生成规则

- 每日景点以地理相邻为优先原则。
- 默认每日安排 2–4 个主要活动。
- 城市间移动日降低行程密度。
- 避免连续步行、频繁换乘和重复折返。
- 亲子、老人用户默认降低步行和夜间活动强度。
- 对需预约或季节性活动明确标注。

### 7.2 信息可信度规则

| 信息类型 | 处理规则 |
|---|---|
| 行程建议 | 可基于模型与目的地知识生成 |
| 景点营业时间 | 标记来源与更新时间 |
| 天气 | 调用实时天气服务 |
| 机票与酒店价格 | 使用实时或缓存数据，注明价格为参考 |
| 签证与入境政策 | 优先使用官方信息源 |
| 用户护照和身份信息 | 默认不保存，除非用户明确授权 |

### 7.3 错误与降级

- 实时数据不可用时，明确提示“当前无法获取实时价格”。
- 无法确认的信息不得编造。
- 行程存在冲突时，展示风险提示而非直接忽略。
- 用户请求违法、危险或不符合当地规定的活动时，拒绝并提供安全替代建议。

## 9. 核心 API 草案

| 接口 | 方法 | 用途 |
|---|---|---|
| `/api/trips` | `POST` | 新建旅行草稿 |
| `/api/trips/{id}` | `GET` | 获取行程详情 |
| `/api/trips/{id}` | `PATCH` | 更新旅行基本信息 |
| `/api/trips/{id}/chat` | `POST` | 向智能体发送需求或修改指令 |
| `/api/trips/{id}/generate` | `POST` | 生成首版行程 |
| `/api/trips/{id}/replan` | `POST` | 局部或全局重规划 |
| `/api/trips/{id}/days/{day}` | `PATCH` | 修改某天行程 |
| `/api/trips/{id}/share` | `POST` | 创建分享链接 |
| `/api/trips/{id}/export` | `GET` | 导出 Markdown 行程内容 |

## 10. 验收标准

### 行程生成

- 用户填写或对话提供目的地和时长后，可生成行程。
- 7 天以内行程的首版生成目标为 30 秒内。
- 每一天包含至少一个活动、交通建议和预算估算。
- 行程不能出现日期缺失、重复天数或跨城逻辑错误。

### 修改能力

- 用户可用自然语言修改预算、节奏、兴趣或单日内容。
- 被锁定活动在局部重规划后保持不变。
- 修改后展示受影响日期与预算变化。

### 数据与可靠性

- 实时信息应标注来源或更新时间。
- 缺失实时数据时不能伪造结果。
- 用户行程可自动保存并在刷新后恢复。

## 11. 关键指标

| 指标 | MVP 目标 |
|---|---:|
| 首次行程生成完成率 | ≥ 80% |
| 首版行程平均生成时间 | ≤ 30 秒 |
| 用户完成保存率 | ≥ 35% |
| 用户进行至少一次修改比例 | ≥ 30% |
| 分享率 | ≥ 10% |
| 生成后负面反馈率 | ≤ 10% |

## 12. 后续版本方向

- 实时航班、火车、酒店与门票数据。
- 地图可视化与路线导航。
- 多人协作编辑与投票。
- 行程中天气、延误和营业时间变更提醒。
- 接入预订平台。
- 旅行账本、报销与费用分摊。
- 个性化长期偏好学习。
